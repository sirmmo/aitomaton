Errors in.
Fixes out.

aitomaton watches the errors of everything running on your Docker Swarm. It reads each one as a single event, as part of a burst, and as a long-term pattern, for one service or across a whole architecture. Then it decides what to do. When the answer is "this is a bug in our code", a coding agent gets a ready-to-push clone and a full brief, and a pull request comes back.

See the live demo Source on GitHub Quick start

How it works

One small service with no dependencies beyond Python's standard library. Webhooks or polling bring errors in, and every tick turns them into findings, decisions and work.

Ingest

Sentry / urgentry webhooks and API polling, Alertmanager alerts. Everything becomes per-minute occurrences.

Discover

Swarm service labels say where each service's source is, what it depends on, and what aitomaton may do.

Analyse

Single errors, bursts and trends per issue, per service and per architecture, including cascades.

Decide

Rules, then laya, JEV and an LLM, each asked only when the last is unsure. Capped by policy.

Act

A stairway space with a prepared clone; the agent fixes, tests and pushes, and aitomaton opens the PR.

Three horizons, three scopes

One exception, a storm of them, and a slow creep over two weeks call for different responses. So does a failure in one app versus the whole stack failing because its database did.

When the front end times out because the database is down, only the database is a root cause. Downstream services are reported, never "fixed".

Cheap decisions first

Every tier answers the same three things: an action (ignore, watch, report, fix), a confidence, and the probability that it is a code defect. The next tier is asked only when the stakes are real and the last answer is unsure or disagrees. A tier that is down hands over to the next.

The swarm is the configuration

There's no registry of apps to keep in sync. Put a few labels on a service and aitomaton knows its repo, its Sentry project, what it depends on, which agent to use, and how far it may go.

  • Reads holodocker's labels (holodocker.repo, …repo_ref, …repo_path)
  • Never fixes third-party images: an image's source label is only a hint until you opt in
  • Credentials by name: the label names a token held in env or a Docker secret; tokens can also be per repo owner or global
  • Per-service agent and model: Claude Code, opencode, crush or openclaude, with any OpenRouter model
# any service in a stack
deploy:
  labels:
    aitomaton.repo: https://github.com/acme/shop-api
    aitomaton.ref: main
    aitomaton.policy: pr          # observe|report|pr|push
    aitomaton.sentry.project: shop-api
    aitomaton.depends: db
    aitomaton.test: pytest -q
    aitomaton.agent: opencode
    aitomaton.model: qwen/qwen3-coder
    aitomaton.git.credential: acme  # a name, not a token
    aitomaton.notes: "never touch migrations/"
observe

Analyse and decide, record only.

report

Open a GitHub issue with the full analysis.

pr

Fix in a stairway space, deliver a pull request.

push

Push to the branch when the tests pass, open a PR otherwise.

The swarm itself, too

Nodes, managers, replicas and task errors are watched like any error stream. Their issues go to an infrastructure outlet: the repo with your stack files, not the application's.

  • Cluster conditions: a node down, an unreachable manager, a lost raft quorum. These are always reports: no commit fixes a dead host.
  • Service conditions: OOM kills, images that do not pull, tasks no node accepts, port conflicts, too few replicas, paused updates.
  • Causes linked: services short of replicas because a node died are the node's problem.
  • Third-party safe: when traefik is OOM-killed, the PR raises its limit in your stack file and leaves traefik alone.
# the global outlet
AITOMATON_INFRA_REPO=acme/infra
AITOMATON_INFRA_PATH=stacks/
AITOMATON_INFRA_POLICY=pr

# or per service, even on third-party images
deploy:
  labels:
    aitomaton.infra.repo: acme/edge-deploy
    aitomaton.infra.path: stacks/edge.yml

# → swarm:edge_traefik:oom
#   fix → aitomaton/fix-edge_traefik-oom
#   "memory limit 128 MiB → 384 MiB"

When a PR is not enough

Policies have two layers. While production is down, the emergency layer applies: it can push instead of opening a PR, notify, and act on the swarm directly.

  • Emergencies by rules: a lost quorum, a service at 0 replicas, OOM kills that leave it short, an error burst right after a deploy.
  • A fixed runbook: restart, roll back, raise the memory limit. aitomaton runs it through the Docker API, one step at a time, each step checked before the next. No model gets write access to the swarm.
  • Bounded: off unless AITOMATON_ACT=1, per-service veto, at most a few actions an hour, never on outages older than aitomaton itself.
  • Told where you are: a Telegram bot (global chats, plus a team's group per service) or any Slack-compatible webhook.
  • Then made permanent: the direct action buys time; the PR to the stack file is the fix.
deploy:
  labels:
    aitomaton.policy: pr
    aitomaton.policy.emergency: push+act

# 03:12 shop_api 0/3 replicas, deployed 03:04
#   EMERGENCY → notify
#   rollback        done   (03:13)
#   restart         —      recovered at 03:15
#   fix → push      when the tests pass

Tell it what no log shows

aitomaton is an MCP server too. Ask it what is going on, or report what no log shows: slowness, strange behaviour, wrong data. It investigates each report and decides on it like any other issue.

  • Status tools: overview, a service, an issue with every decision's reasoning.
  • Investigated: replicas, failing tasks, recent deploys, related errors and alerts, swarm conditions and metrics at the time of the report.
  • Merged and weighed: more people reporting the same thing weigh more; a corroborated report weighs more than a lone one.
  • Never on someone's word alone: a critical report pages people, but never triggers direct actions.
  • Or through Telegram: the bot asks for what is missing and confirms before it files the report, then follows it up in the chat. People outside the team get plain answers and never see the internals.
# claude mcp add --transport http aitomaton …/mcp
report_issue(
  title="newsroom site very slow",
  service="newsroom_api", kind="slowness")

# → user:newsroom_api:1, corroborated
#   newsroom_api runs 0 of 1 replicas.
#   4 tasks failed in the last hour.
#   The service was updated 246 minutes ago.
#   decision: report

A space to fix it in

A fix becomes a stairway experiment: a folder on your server with a coding agent in it, visible in claude.ai/code so you can watch or take over.

  • Prepared clone. aitomaton clones the repo with the service's own token and checks out aitomaton/fix-…. The agent only commits and pushes.
  • A complete brief. The stack trace, breadcrumbs, release, analysis and metrics, plus how to deliver under the policy.
  • A result protocol. The agent ends with AITOMATON-RESULT; aitomaton opens the PR and deletes the credential.
  • Bounded. Dry-run by default, plus limits on concurrent and daily fixes, and a cooldown per issue.

Quick start

Requirements: a swarm manager, a Sentry or urgentry, and optionally stairway, laya, an OpenRouter key and GitHub tokens. Start in dry-run, read its decisions for a few days, then let it act.

  • Webhook: POST /hooks/sentry (HMAC-verified)
  • Alerts: POST /hooks/alertmanager?token=…
  • Agent callbacks: POST /hooks/stairway
  • Output: GET /status.json and GET /
git clone https://github.com/sirmmo/aitomaton
cd aitomaton
docker build -t aitomaton:0.1 .
docker build -t aitomaton-laya:0.1 laya

cp .env.example .env
# SENTRY_URL / SENTRY_TOKEN / SENTRY_ORG
# STAIRWAY_URL / STAIRWAY_TOKEN
# JEV_MODEL=typesafe/jev-router, LLM_API_KEY
# AITOMATON_GIT_TOKEN_<OWNER>=…
# AITOMATON_DISPATCH=0  ← dry run first

docker stack deploy -c stack.yml aitomaton
